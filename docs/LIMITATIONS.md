# Known limitations

Stated explicitly, as required. None of these are hidden in the code; each
corresponding module's docstring says the same thing at the point where it
matters.

## No physical hardware was available

This project was built with no SX1280, UWB, Wi-Fi RTT, BLE, or GNSS
hardware attached. Consequences:

- There is no `MEASURED_HARDWARE` evidence anywhere in this codebase. The
  only real ranging measurements it contains are Stuart Robinson's six
  published short-range points (`PUBLISHED_EXPERIMENT`).
- `hardware/sx1280_measurements.py` (the raw measurement schema and CSV
  importer) is fully implemented and unit-tested, but has only been
  exercised against synthetic test CSVs, never a real device log.
- The SX1280 error model in `hardware/sx1280_error_model.py` bootstrap-
  resamples from those six published points. It is explicitly not a
  validated model beyond the 0-250 m range those points cover, and it does
  not condition on bandwidth, spreading factor, temperature, or any other
  variable, because six unrepeated points cannot support fitting one.
- `examples/gnss_sample_log.csv` is synthetic (`SIMULATED_MONTE_CARLO`),
  not a real receiver capture.

## Network access was blocked during development

Outbound HTTPS to manufacturer, distributor, and standards-body pages
returned `EGRESS_BLOCKED` for every domain tried. See `docs/SOURCES.md`
for exactly which two facts were confirmed via search-engine snippets and
which sources were not re-verified this session. Numeric hardware
specification fields (TX power, RX sensitivity, currents) that the author
was not confident of from memory are left `None` in the hardware profile
registry rather than filled with a guessed number.

## Range-error models are configured, not physically simulated

Every method except SX1280 uses a Gaussian/NLOS-bias model whose
parameters (`timing_uncertainty_m`, `nlos_probability`, `nlos_bias_m`,
`additional_measurement_uncertainty_m`) come directly from the scenario
configuration. This satisfies the requirement not to simulate unnecessary
RF/electrical detail, but it also means an accuracy result for, say, a
UWB TDoA scenario reflects the uncertainty you configured, not an
independent physical prediction of UWB TDoA accuracy. Only the SX1280
hardware-calibrated model is driven by real (published) measurements.

## GNSS import is a flat CSV schema, not a binary protocol parser

`gnss/model.py` reads this project's own documented CSV column schema. It
does not parse NMEA sentences, u-blox UBX binary frames, or RINEX
observation files. A receiver export or a conversion script would need to
produce the CSV schema documented in `docs/FIELD_DEFINITIONS.md` first.

## Anchor layouts and default paths are simple presets

`tables/pipeline.py`'s `default_anchor_layout` and `default_path` exist so
a scenario spec that only fixes environment dimensions can still run.
They are deterministic corner/diagonal presets, not a coverage-optimized
layout or a site-surveyed path. A real deployment plan should supply its
own anchor coordinates and path.

## Energy and cost tables are empty in a generated workbook by default

`metrics/energy.py` and `metrics/cost.py` are fully implemented and
unit-tested (`EnergyBudget`, `CostBreakdown`, `estimate_battery_life`,
`cost_per_area`, and so on), but `ScenarioTemplate` has no power-draw or
cost-per-unit fields, and the CLI pipeline does not currently prompt for
or populate them automatically. As a result, the `energy` and `cost`
sheets in a workbook generated by `run-all` are empty placeholders unless
a caller uses the library directly to attach an `EnergyBudget`/
`CostBreakdown` to a scenario. This is a real gap in the end-to-end CLI
workflow, not a missing feature in the underlying metrics code.

## Several methods share one generic solver

`GENERIC_RTT`, `WIFI_RTT_FTM`, `RSSI_TRILATERATION`, `ACOUSTIC_RANGING`,
and `SX1280_RANGING` (when run through the Monte Carlo pipeline in a
multilateration configuration) all reuse the same absolute-range TWR/ToA
solver. There is no method-specific propagation model (multipath for
Wi-Fi RTT, path-loss-based RSSI conversion, acoustic attenuation, and so
on) here, per the requirement not to build a bespoke detailed simulator
for every method; where a method lacks a justified model, this project
uses sourced/imported evidence instead (see `methods/catalog.py`'s
`evidence_note` for methods with `has_native_simulator=False`).

## Path tracking metrics use a numerical tangent approximation

`metrics/path_metrics.py`'s along-track/cross-track error uses a finite-
difference estimate of the true path's local tangent direction. This is
exact for a straight line and an approximation elsewhere (e.g. near sharp
turns in a box-perimeter or staircase path).

## Not modeled at all (by design, not oversight)

- Reacquisition time after an outage (no tracking/filtering state exists
  to reacquire from).
- Queue delay (no queueing model exists).
- Slotted ALOHA, CSMA, or any MAC protocol beyond plain scheduled/TDMA-like
  and pure ALOHA.
- A live spreadsheet formula engine: the workbook is fully pre-computed by
  Python, so there is no "formula recalculates to an error" failure mode
  to check for beyond the defensive literal-error-token scan this project
  does perform.

## Field catalog descriptions are generated, not individually hand-written

`tables/master_fields.py` infers each field's category and unit from its
prefix/suffix and builds a description naming the source field and
category. With 300+ fields, this keeps the catalog consistent and
guaranteed to match the real columns, at the cost of each description
being a short, formulaic sentence rather than a bespoke paragraph.

## Platform and environment

Built and tested in a Linux x86_64 container with Python 3.11.
`scripts/run.sh` (bash) has been executed and verified end to end
repeatedly in that environment, including from a clean ZIP extraction with
no access to the original checkout (see `docs/VALIDATION.md`).

`scripts/run.ps1` (Windows PowerShell) was added to mirror `run.sh` step
for step and reviewed carefully for PowerShell syntax and semantics, but
**it has not been executed on an actual Windows machine or under
PowerShell at all** - no Windows environment or PowerShell interpreter
(including PowerShell Core / `pwsh`, which runs on Linux) was available
in the environment this project was built in. The underlying Python code
it drives (the CLI, the test suite) has no Windows-specific code path and
uses `os.path.join`/`pathlib`-safe path construction throughout, so it is
expected to work; the untested part is specifically the PowerShell script
itself (parameter binding, `$LASTEXITCODE` propagation across the exact
PowerShell version a user has, and execution-policy interaction). If it
does not work as written, every command it runs is one line - see
"Running it yourself, step by step" in `README.md` - and can be typed
directly into PowerShell or `cmd.exe` with a normal `venv`/`pip` setup.

Regression tests (`tests/test_run_scripts.py`) check both scripts exist,
have balanced braces, and cover the same seven phases; `run.sh`
additionally passes a real `bash -n` syntax check in CI/test runs on
Linux. No equivalent real syntax check exists for `run.ps1` in this
environment, for the reason above.
